# 사용 가이드

프로젝트에 적용하는 방법, 필요한 문서, 이후 작업과 갱신 방법을 정리한다. Codex가 따라야 할 상세 적용 절차는 [BOOTSTRAP.md](../BOOTSTRAP.md)에 있다.

## URL 한 줄로 적용하기

대상 프로젝트를 연 Codex 채팅에서 다음과 같이 요청한다.

```text
https://github.com/Jhoae/codex-project-workflow 를 현재 프로젝트에 적용해줘.
```

Codex는 [BOOTSTRAP.md](../BOOTSTRAP.md)를 따라 원본 지침과 템플릿을 검토하고, 대상 프로젝트의 실제 코드·문서·설정·Git 상태·검증 환경을 조사한다. 이후 기존 문서 체계를 보존하며 확인된 목표·명령·상태·결정으로 지침과 문서를 채운다. 빈 템플릿 복사만으로 적용을 완료하지 않는다.

- 기존 `AGENTS.md`는 덮어쓰지 않고 중복을 제거하며 비파괴 병합한다.
- 현재 테스트의 실행 여부, 알려진 실패, CI 연결과 검증 공백을 구분한다.
- 확인하지 못한 사실은 `Unknown`, 미실행 검사는 `Not Run`으로 남긴다.
- 원본 URL과 확인 가능한 revision을 기록한다. 원본 변경이 기존 프로젝트에 자동 반영되지는 않는다.
- 최초 적용에는 원본 지침과 템플릿을 검토하지만, 이후 일반 작업에서는 관련 문서만 읽는다.
- 웹·GitHub에 접근할 수 없으면 원본을 로컬에 제공하고 같은 절차를 수행한다.

이 요청의 기본 범위는 읽기 전용 조사와 프로젝트 문서 생성·병합·검증이다. 기능 구현, 새 의존성 설치, 배포, 외부 시스템 수정, Git commit·push·PR은 별도 요청이나 이미 확인된 권한 범위에 따라 수행한다.

**문서 적용 완료와 검증 환경 준비 완료는 별도로 보고한다.** 테스트나 CI가 부족해도 사실대로 문서화하고 검증 공백을 다음 작업으로 남길 수 있다. 이 상태를 높은 자율 실행이나 배포가 준비됐다고 표현하지 않는다.

## 기본 작업 흐름

```text
관련 사실 확인
→ UI·소비자 관점에서 결과와 인수 조건 정의
→ 위험·허용 범위·필수 검증 결정
→ 작은 Step 구현
→ 검사하고 필요한 수정 반복
→ 결과와 증거 기록
→ 다음 Step 또는 Handoff
```

**인수 조건**은 결과를 받아들일 기준이다. 예를 들어 초대 링크의 만료 정책을 정했다면, 만료 직전·동일 시각·직후의 처리와 거부 후 상태를 확인한다. 기대 결과는 사용자 요구나 확정된 계약에서 가져온다.

**검증**은 변경이 잘못될 수 있는 지점을 확인한다. 관련 테스트, 실제 사용자 흐름, 필요한 수동 확인을 선택한다. 중요한 규칙은 일부 조건을 틀리게 바꿔 테스트가 잡아내는지 확인할 수 있다. 자세한 방법은 [검증 가이드](verification.md), 작업 크기에 따른 차이는 [적용 예시](../examples/verified-work.md)를 참고한다.

**자율 실행**은 이미 허용된 범위에서 구현·검사·수정을 이어가는 것이다. 매 Step마다 승인을 다시 받지 않는다. 중요한 정책이 미확정이거나 권한 범위를 벗어나면 그 결정을 분리하고, 독립적으로 가능한 작업은 계속한다.

## 문서는 필요한 만큼만 만든다

| 파일·책임 | 역할 |
|---|---|
| [AGENTS.md](../AGENTS.md) | 반복 적용할 핵심 작업 규칙 |
| [BOOTSTRAP.md](../BOOTSTRAP.md) | 기존 프로젝트에 맞게 적용하는 절차 |
| [PROJECT_CONTEXT.md](../templates/PROJECT_CONTEXT.md) | 현재 상태·제약·검증 공백·다음 시작점 |
| [BACKLOG.md](../templates/BACKLOG.md) | 전체 결과와 우선순위, 필요한 검증 환경 개선 |
| [WEEKLY_TODO.md](../templates/WEEKLY_TODO.md) | 현재 기간의 Step·인수 조건·검증 증거 |
| [DECISION_LOG.md](../templates/DECISION_LOG.md) | 중요한 선택의 이유·대안·대체 관계 |
| [TECHNOLOGY_DECISION.md](../templates/TECHNOLOGY_DECISION.md) | 되돌리기 어려운 기술·구조 결정 |
| [TROUBLESHOOTING.md](../templates/TROUBLESHOOTING.md) | 재사용할 문제 해결 지식과 재발 방지 검사 |

기존 이슈·문서 체계가 있으면 우선 재사용한다. 작은 프로젝트는 아래 두 파일로 시작하고, Context의 섹션으로 활성 작업·결정·검증을 함께 관리할 수 있다.

```text
AGENTS.md
docs/project-context.md
```

내용이 커지면 Backlog, 현재 Todo, 결정 기록 등을 분리하고 Context에서 연결한다. 기존 기본 경로인 `docs/backlog.md`, `docs/todo/YYMMDD~YYMMDD.md`, `docs/decisions.md`, `docs/technology-decisions/`, `docs/troubleshooting.md`는 계속 사용할 수 있다. 내용이 없는 선택 문서나 빈 archive 파일은 만들지 않는다.

- Todo는 Step 시작·검증 직후·중요한 변화에 갱신한다.
- Context는 목표·현재 상태·다음 시작점이 바뀌거나 작업을 인계할 때 갱신한다.
- 중요한 결정과 재사용할 문제 해결 지식은 해당 기록에 남긴다.
- 원본 로그와 테스트 내용을 반복 복사하지 않고 증거 위치를 연결한다.
- 완료된 기간 기록과 오래된 증거는 검색 가능하게 보존한다.

## 완료는 이렇게 판단한다

1. 요청 범위의 인수 조건을 충족했다.
2. 사전에 정한 필수 검사가 통과했다.
3. 검증 증거가 현재 코드 상태와 연결되어 있다.
4. 테스트·검사 기준을 바꿨다면 이유와 보완 근거가 있다.
5. 관련 문서가 현재 상태와 일치하고 남은 한계를 설명할 수 있다.

필수 검사에 `Fail`, `Blocked`, `Not Run`이 남으면 `Done`이 아니다. 구현 완료·검증 완료·배포 가능 여부를 구분한다. 검사 통과만으로 배포나 운영 데이터 변경 권한이 생기지는 않는다.

## 적용 후 작업 요청 예시

```text
AGENTS.md와 현재 작업에 관련된 문서를 확인해줘.
[원하는 결과]의 인수 조건, 변경 범위, 필요한 검증을 먼저 정리하고,
이미 허용한 범위에서는 작은 Step으로 구현·검증·수정을 끝까지 진행해줘.
결과를 크게 바꾸는 미확정 정책이나 권한 밖의 작업은 따로 알려줘.
검증 결과와 증거, 미검증 사항, 다음 시작점만 필요한 문서에 남겨줘.
```

계획 검토만 원하면 구현 전 제안까지 요청 범위를 지정한다. 기본 주기는 1주이지만 작업 세션이나 스프린트로 조정할 수 있다. 검증이 끝난 Step은 기간 종료와 관계없이 완료 처리한다.

## 기존 적용 프로젝트를 갱신할 때

다시 적용을 요청하면 이전 workflow revision과 현재 지침의 차이를 확인하고 프로젝트별 규칙을 보존하며 병합한다. 기존 기록은 지우거나 과거 검증을 새 기준의 통과로 바꾸지 않는다. 앞으로 수행할 작업부터 새 인수 조건과 증거 형식을 사용한다.

기능 변경 하나와 버그 수정 하나에 먼저 적용해 전체 작업 시간, 검사·문서 비용, 발견한 반례, 재작업, 사람의 개입 이유를 살펴본다. 필요한 검증이 실제 실패를 잡는지 확인한 뒤 적용 범위를 넓힌다.
