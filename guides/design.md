# 설계 배경

이 워크플로는 사용자에게 필요한 결과를 먼저 정하고, 작은 변경을 검증하며, 작업의 근거를 다음 세션에 남긴다. 반복해서 적용할 규칙은 [AGENTS.md](../AGENTS.md)에 둔다.

## UI에서 출발해, 테스트로 신뢰를 쌓는다는 것

UI가 있으면 화면과 사용자 행동에서 요구사항을 역산한다. 화면부터 코딩한다는 뜻은 아니다. UI가 없으면 API 호출자, 명령, 데이터 사용처처럼 결과를 소비하는 대상을 기준으로 삼는다.

테스트 개수보다 잘못된 결과를 잡아내는지가 중요하다. 구현 전에 성공 조건을 정하고, 작업의 위험에 맞는 테스트와 실제 동작 확인으로 결과를 판단한다. 명확한 기준과 반복 가능한 검증이 쌓인 영역부터 코드 리뷰의 부담을 줄인다.

## 무엇을 유지하고 바꾸는가

| 구분 | 내용 | 이유 |
|---|---|---|
| 유지 | UI·소비자 관점에서 요구사항 역산 | 실제 사용자가 원하는 결과를 구현과 검증의 기준으로 삼기 위해 |
| 유지 | 독립적으로 검증 가능한 작은 Step | 실패 원인과 변경 영향을 좁히고 빠르게 수정하기 위해 |
| 유지 | 사실·가정·결정 구분과 파일 기반 인계 | 다음 세션이 추측 없이 현재 상태와 근거를 이어받기 위해 |
| 유지 | 기존 문서·코드·사용자 변경 보존 | 프로젝트의 맥락과 이미 진행한 작업을 지키기 위해 |
| 줄임 | 매 Step의 세세한 설명과 문서 반복 갱신 | 중요한 판단과 결과에 기록을 집중하기 위해 |
| 버림 | 모든 중간 실패를 영구 문서에 옮기는 방식 | 재사용할 지식과 일상적인 시행착오를 구분하기 위해 |
| 버림 | 검사 수행 자체를 느슨한 완료 근거로 삼는 표현 | 필수 검사의 결과와 실제 인수 조건을 충족해야 완료로 보기 위해 |
| 추가 | 구현 전 인수 조건과 기대 결과의 근거 | AI가 구현에 맞춰 정답을 만들어내지 않도록 하기 위해 |
| 추가 | 테스트의 검출력과 검증 기준 변경 점검 | 잘못된 구현이나 약화된 검사도 통과하는 문제를 줄이기 위해 |
| 추가 | 위험과 검증 공백에 따른 자율 범위 | 허용된 일은 계속 진행하면서 중요한 결정에는 필요한 판단을 남기기 위해 |
| 추가 | 코드 상태와 연결된 검증 증거 | 어떤 변경을 실제로 확인했는지 다시 확인할 수 있게 하기 위해 |

주간 계획은 유지하되 프로젝트 리듬에 맞게 조정한다. 모든 코드 리뷰 폐지, coverage 100%, 매 작업 mutation testing, 항상 다중 에이전트 사용은 공통 규칙으로 추가하지 않는다.

## 설계 참고와 적용 범위

[Uncle Bob의 글](https://x.com/unclebobmartin/status/2080257779395154409)은 강한 제약과 검사를 바탕으로 에이전트의 결과를 신뢰한다는 개인 전략을 설명한다. 이 workflow는 그 관점을 기존의 소비자 중심 설계와 작은 검증 단위에 연결했다. 위험별 검사, 자율 범위, 기록 간소화는 이 저장소의 적용 제안이다.

검증 체계가 성숙한 영역부터 사람이 세부 구현을 확인하는 부담을 줄일 수 있다. 중요한 정책·권한·데이터·구조와 제품의 사용성에 필요한 판단은 계속 남긴다. 관련 근거와 방법은 [검증 가이드](verification.md)에 정리했다.

일반적인 개발 개념은 필요한 범위에서 사용한다. 특정 제품이나 스택은 범용 기본값으로 강제하지 않으며, 프로젝트별 새 도구는 필요성·대안·비용을 근거로 제안한다. 비밀값·개인 정보·개인 환경의 절대 경로는 범용 문서에 남기지 않는다.
