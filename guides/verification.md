# 검증 기준을 정하는 방법

이 문서는 검증 정책을 처음 만들거나 중요한 검증 공백을 해결할 때 참고한다. 매 작업마다 전체를 읽을 필요는 없다. 프로젝트에 적용할 때는 실제 명령·계약·환경에 맞게 기존 지침이나 검증 문서에 필요한 내용을 반영한다.

## 1. 무엇을 정답으로 볼지 먼저 정한다

인수 조건은 결과를 받아들일 기준이다. 사용자 요구·도메인 규칙·기존 계약을 근거로, 관찰할 수 있는 사례로 표현한다.

| 조건 | 기대 결과의 근거 | 확인할 사례 | 검증 방법 |
|---|---|---|---|
| 이 작업이 만족할 동작 | 요구사항·확정 정책·공개 계약 | 정상·실패·관련 경계 | 기존 테스트 경로·명령·수동 절차 |

- 현재 구현을 그대로 설명한 테스트로 정답을 정하지 않는다.
- 버그 수정에서는 기존 계약을 확인하고 수정 전 실패와 수정 후 성공을 비교한다. 환경 오류로 실패한 것은 버그 재현 증거가 아니다.
- 리팩터링에서는 보존할 동작과 외부 계약을 먼저 확인한다.
- 디자인·사용성·사업 정책 등 자동 판정이 어려운 부분은 사람이 확인할 내용과 시점을 정한다.
- 작은 작업은 표 대신 짧은 문장이나 기존 검사 링크로 충분하다.

## 2. 위험과 공백으로 필수 검사를 고른다

검사 수를 늘리기 전에 이 변경이 무엇을 잘못 만들 수 있는지 확인한다.

| 위험 | 확인할 내용의 예 |
|---|---|
| 사용자 동작 | 성공·빈 상태·실패·복구 흐름, 실제 데이터 연결 |
| 공개 계약 | 입력·출력·오류, 기존 호출자와의 호환성 |
| 권한·결제 | 허용과 거부 경로, 우회 요청, 중복 처리, 실패 후 상태 |
| 데이터 변경 | 보존 조건, 호환성, migration, 필요한 복구 절차 |
| 구조·성능 | 의존 경계, 유지보수 영향, 대표 부하와 비교 기준 |

기존 테스트·lint·typecheck·build·통합 검사 중 해당 위험을 확인하는 검사를 선택한다. 검증 공백이 있으면 먼저 필요한 검사를 마련하거나, 허용된 안전한 구현을 진행하면서 미검증 상태를 명시한다. 필수 검증이 남은 작업은 완료로 닫지 않는다.

새 도구가 필요하면 필요성·대안·실행 비용·적용 범위를 검토한다. coverage 100%, 모든 변경의 mutation testing, 특정 BDD 도구를 범용 조건으로 삼지 않는다. 중요한 로직에 집중하거나 비용이 큰 검사를 별도 주기로 수행할 수 있지만, 현재 작업의 필수 검사를 사후에 조용히 제외해서는 안 된다.

## 3. 테스트가 잘못된 결과를 잡는지 확인한다

- 핵심 규칙에는 틀린 입력·경계값·거부 경로를 확인한다.
- 필요하면 소스 조건을 변형하는 mutation testing으로 검사 능력을 확인한다. 변형이 살아남으면 테스트 공백인지, 동작이 같은 변형인지 조사한다.
- 인수 사례의 중요한 값을 바꾸어 테스트가 실제 애플리케이션 동작에 연결되어 있는지 확인할 수도 있다. 이 방법은 소스 코드 변형과 구분한다.
- coverage는 실행 공백을, mutation 결과는 선택된 변형의 검출 여부를 보여준다. 요구사항 자체의 누락까지 보장하지 않는다.
- 점수와 함께 대상·제외 범위·중요한 미검출 항목을 확인한다. 품질 수치만으로 완료를 판정하지 않는다.

별도 검토자는 요구사항에서 반례를 먼저 찾고 구현·테스트·검사 설정을 함께 확인한다. 같은 모델 또는 다른 모델이라는 이유만으로 판단의 독립성을 가정하지 않는다.

## 4. 기준 변경을 드러내고 실제로 실행한다

테스트 삭제·skip·assertion 완화·과도한 mock·coverage 제외·임계값 변경·CI 검사 제거가 포함되면 다음을 확인한다.

1. 요구사항이나 계약이 바뀐 것인가? 근거와 변경 이유가 있는가?
2. 기존에 잡던 실패를 놓치게 되는가? 보완 검증이 있는가?
3. 중요한 정책·운영 경계 변경이 현재 권한 안에 있는가?

필수 검사는 실제 명령 또는 재현 가능한 수동 절차에 연결한다. CI·병합 체계가 있으면 중요한 자동 검사를 그 조건에 연결한다. 없는 프로젝트는 현재 확인 방법과 강제되지 않는 한계를 기록하고, 위험에 따라 자동화 보완을 후속 작업으로 정한다. 새 CI 도입을 모든 작업의 선행 조건으로 삼지 않는다. 지침 문서 작성, CI 설정 존재, 검사의 실제 실행과 강제 여부를 구분하고 접근할 수 없는 설정은 미확인으로 남긴다.

## 5. 증거를 현재 변경에 연결한다

최종 결과에서 검사 대상 코드 상태, 환경, 실행 명령 또는 수동 절차, 결과, 증거 위치를 찾을 수 있어야 한다. CI 실행 링크나 하나의 증거 묶음으로 공통 정보를 공유할 수 있다.

- 미커밋 변경은 commit SHA만으로 식별되지 않는다. diff 스냅샷 등으로 검사한 변경을 식별한다.
- 관련 코드·테스트·설정이 바뀌면 영향을 받는 검사를 다시 실행한다.
- 기존 실패와 이번 변경의 실패를 구분하되, 필수 검사의 실패를 성공으로 취급하지 않는다.
- 네트워크·권한·환경 때문에 실행하지 못한 검사는 `Blocked` 또는 `Not Run`이다.
- 결과 요약과 원본 로그를 중복 복사하지 않는다. 증거를 보관할 때 비밀값·개인 정보를 제거한다.

## 6. 작은 시범으로 검증 비용을 확인한다

기능 변경 하나와 버그 수정 하나에 먼저 적용한다. 전체 작업 시간, 검사·문서 비용, 발견한 반례, 재작업, 사람이 개입한 이유와 미검증 사항을 살펴본다. 짧은 시범에서 문제가 없었다는 사실만으로 신뢰성이 입증됐다고 주장하지 않는다.

실제로 중요한 실패를 잡고 반복 비용을 줄이는 검사를 남긴다. 검증 경험이 쌓인 영역부터 자율 범위를 넓히고, 중요한 공백은 Backlog의 정식 작업으로 관리한다.
