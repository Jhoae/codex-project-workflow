# Codex Project Workflow

특정 기술이나 저장소 구조에 종속되지 않는 프로젝트 실행 지침과 문서 템플릿 모음이다. Codex가 프로젝트를 시작할 때 사실을 확인하고, UI 또는 소비자 관점에서 요구사항을 역산하고, 전체 Backlog와 주 단위 Todo를 연결하고, 작업을 작은 Step으로 나누어 구현·검증·기록하도록 돕는다.

이 저장소의 목표는 많은 문서를 만드는 것이 아니다. **현재 상태, 결정, 실행 범위, 문제 해결 지식을 서로 다른 책임으로 관리해 다음 작업이 추측이 아니라 증거에서 시작되게 하는 것**이다.

## URL 한 줄로 적용하기

새 프로젝트를 연 Codex 채팅에서 다음과 같이 요청한다.

```text
https://github.com/Jhoae/codex-project-workflow 를 현재 프로젝트에 적용해줘.
```

이 요청에서 **적용**은 원본 Markdown을 그대로 복사하는 작업이 아니다. Codex는 [`BOOTSTRAP.md`](BOOTSTRAP.md)를 먼저 읽고 다음 결과를 만들어야 한다.

- 저장소의 모든 지침과 템플릿을 검토한다.
- 대상 프로젝트의 코드, 문서, 설정, 테스트, Git 상태를 먼저 조사한다.
- 기존 문서 체계를 보존하면서 각 문서의 책임을 매핑한다.
- 생성하는 문서를 실제 프로젝트의 목표, 구조, 명령, 상태, 결정으로 채운다.
- 확인되지 않은 내용은 추측하지 않고 미확정 사항으로 남긴다.
- 이후 Codex 채팅이 파일을 통해 현재 상태를 이어받도록 로컬 `AGENTS.md`와 프로젝트 문서를 연결한다.

웹 또는 GitHub 접근이 불가능한 환경에서는 원격 저장소를 읽을 수 없으므로, 이 저장소를 로컬에 제공한 뒤 같은 요청을 해야 한다.

적용은 실행 시점의 저장소 내용을 대상 프로젝트에 구체화하는 작업이다. 이후 이 원본 저장소가 변경되어도 기존 프로젝트가 자동 갱신되지는 않으므로, 적용 시 원본 URL과 확인 가능한 revision을 Context에 기록하고 필요할 때 다시 적용한다.

## 핵심 작업 방식

1. 구현 전에 사실과 성공 조건을 확인한다.
2. UI가 있으면 화면과 사용자 행동에서, UI가 없으면 실제 소비자에서 요구사항을 역산한다.
3. 전체 할 일은 Backlog에, 이번 주에 끝낼 일은 Weekly Todo에 둔다.
4. 현재 할 일을 독립적으로 검증 가능한 작은 Step으로 나눈다.
5. 각 Step을 구현하고 검증한 직후 같은 Todo를 갱신한다.
6. 결정은 Decision Log에, 되돌리기 어려운 기술 선택은 별도 기술 결정 문서에 남긴다.
7. 중요한 문제 해결 과정은 Troubleshooting Log로 분리해 재사용 가능한 지식으로 만든다.
8. 작업을 넘기거나 중단하기 전에 Context / Handoff에 현재 상태와 다음 한 Step을 남긴다.

## 파일 구성

| File | Purpose |
|---|---|
| [`BOOTSTRAP.md`](BOOTSTRAP.md) | URL 적용 요청을 프로젝트 맞춤 문서 체계로 변환하는 필수 절차 |
| [`AGENTS.md`](AGENTS.md) | Codex가 반복 적용할 계획·구현·검증·기록 원칙 |
| [`templates/PROJECT_CONTEXT.md`](templates/PROJECT_CONTEXT.md) | 현재 상태, 제약, 위험, 다음 시작점을 전달하는 context / handoff |
| [`templates/BACKLOG.md`](templates/BACKLOG.md) | 전체 목표와 `Now`, `Next`, `Later`, `Out of Scope` 관리 |
| [`templates/WEEKLY_TODO.md`](templates/WEEKLY_TODO.md) | 한 주의 목표, 작은 Step, 진행 기록, 검증 결과 관리 |
| [`templates/DECISION_LOG.md`](templates/DECISION_LOG.md) | 확정·제안·대체된 결정을 시간순으로 기록 |
| [`templates/TECHNOLOGY_DECISION.md`](templates/TECHNOLOGY_DECISION.md) | 되돌리기 어려운 기술·구조 결정의 근거와 영향 기록 |
| [`templates/TROUBLESHOOTING.md`](templates/TROUBLESHOOTING.md) | 증상, 증거, 원인, 해결, 검증, 한계를 분리해 기록 |

## 프로젝트에 적용하기

### 1. Bootstrap 실행

URL로 적용을 요청받은 Codex는 [`BOOTSTRAP.md`](BOOTSTRAP.md)의 전체 절차를 따라야 한다. 원격 저장소의 파일을 대상 프로젝트에 그대로 복제한 것만으로 적용을 완료했다고 보고할 수 없다.

적용이 완료되려면 최소한 다음 상태가 만들어져야 한다.

- 로컬 `AGENTS.md`에 범용 실행 원칙과 확인된 프로젝트별 규칙이 함께 존재한다.
- 현재 프로젝트 상태, 전체 Backlog, 활성 주간 Todo, 결정, 트러블슈팅의 저장 위치가 정해져 있다.
- 활성 문서는 빈 템플릿이 아니라 실제 프로젝트 조사 결과로 채워져 있다.
- 기존 문서 체계를 사용한 경우 원본 템플릿의 각 책임이 어느 문서로 매핑됐는지 설명할 수 있다.
- 다음 Codex 채팅이 이전 대화 없이도 현재 상태와 다음 Step을 찾을 수 있다.

### 2. 지침 병합

`AGENTS.md`가 없다면 저장소의 범용 지침을 프로젝트 루트에 배치하고 확인된 프로젝트별 명령, 구조, 품질 기준을 추가한다. 이미 존재한다면 덮어쓰지 않고 다음 원칙으로 병합한다.

- 기존 프로젝트 규칙과 사용자 변경을 보존한다.
- 중복되는 규칙은 한 번만 남긴다.
- 프로젝트별 명령과 더 구체적인 규칙이 범용 원칙보다 우선하도록 한다.
- 충돌을 임의로 숨기지 않고 영향이 큰 충돌은 사용자 결정 대상으로 남긴다.
- 일시적인 진행 상태는 `AGENTS.md`가 아니라 Context와 Todo에 기록한다.

Codex는 작업 전에 `AGENTS.md`를 읽고, 저장소 루트에서 현재 작업 디렉터리까지 발견한 지침을 순서대로 결합한다. 더 가까운 디렉터리의 지침으로 특정 영역의 규칙을 구체화할 수 있다. 자세한 동작은 [Codex의 `AGENTS.md` 공식 문서](https://developers.openai.com/codex/guides/agents-md)를 참고한다.

### 3. 문서 책임 매핑

프로젝트에 기존 문서 체계가 없다면 다음 구조를 기본값으로 사용한다.

```text
AGENTS.md
docs/project-context.md
docs/backlog.md
docs/todo/YYMMDD~YYMMDD.md
docs/decisions.md
docs/technology-decisions/
docs/troubleshooting.md
docs/archive/
```

모든 원본 템플릿은 적용 과정에서 반드시 검토한다. 다만 기존 프로젝트가 같은 책임을 수행하는 문서를 이미 가지고 있다면 중복 파일을 만들지 않고 그 위치로 매핑한다.

- Project Context / Handoff, Backlog, 현재 Todo, Decision Log, Troubleshooting Log의 책임은 항상 저장 위치를 정한다.
- Technology Decision은 관련 결정이 있을 때 결정별 문서로 생성한다.
- 보관할 완료 문서나 증거가 생기기 전에는 빈 archive 파일을 만들 필요가 없다.
- 적용하지 않은 템플릿은 `Not Applicable`로 분류하고 이유를 완료 보고에 남긴다.

기존 이슈 트래커나 문서 체계가 있으면 새 체계를 중복 생성하지 말고, 각 템플릿의 책임을 기존 위치에 대응시킨다.

### 4. 프로젝트에 맞게 내용 채우기

대상 프로젝트에 생성하는 활성 문서에는 일반적인 작성 안내를 그대로 남기지 않는다. 조사로 확인한 다음 정보를 실제 값으로 작성한다.

- 프로젝트 목적과 관찰 가능한 성공 조건
- 현재 구현·테스트·배포 상태
- 실제 디렉터리와 주요 구성 요소
- 확인된 실행, 검사, 테스트, 빌드 명령
- 현재 우선순위와 활성 작업
- 확정 결정, 미확정 질문, 위험, 제외 범위
- 검증 결과와 증거 위치
- 다음에 시작할 가장 작은 한 Step

확인하지 못한 정보는 만들어내지 않는다. `Unknown`, `Not Verified`, `Decision Needed`처럼 상태를 명시하고 확인 방법을 함께 적는다.

### 5. 파일 기반 연속성

Codex의 대화 기억을 프로젝트 상태의 주 저장소로 사용하지 않는다. 지속되어야 하는 사실은 프로젝트 파일에 기록한다.

- `AGENTS.md`: 반복 적용할 작업 규칙과 프로젝트별 검증 명령
- Project Context / Handoff: 현재 상태와 다음 시작점
- Backlog: 장기 목표와 우선순위
- 현재 Todo: 진행 중 Step과 실시간 결과
- Decision Log: 확정·대체·미확정 결정
- Troubleshooting Log: 문제 해결 과정과 검증

새 Codex 작업은 로컬 `AGENTS.md`를 통해 이 문서들을 먼저 확인하고, 작업 중 얻은 새 사실을 같은 파일에 갱신한다. 대화가 아니라 파일이 프로젝트의 지속 가능한 기억 역할을 한다.

### 6. 적용 이후 첫 작업 요청

Bootstrap이 완료된 뒤에는 다음과 같이 시작할 수 있다.

```text
AGENTS.md와 현재 프로젝트 문서를 먼저 읽어줘.
현재 상태, 목표, 제약, 미확정 사항을 구분하고,
Backlog와 이번 주 Todo를 정렬한 뒤 첫 번째 검증 가능한 Step만 제안해줘.
UI가 있는 작업은 화면과 사용자 행동에서 필요한 데이터와 계약을 역산해줘.
각 Step 완료 직후 Todo와 관련 기록을 갱신해줘.
```

처음부터 구현을 원하면 마지막 문장을 다음처럼 바꾼다.

```text
계획을 확인한 뒤 안전한 범위에서 구현과 검증까지 진행하고,
각 Step 결과를 문서에 즉시 반영해줘.
```

### 7. 주간 운영

주 초에는 Backlog의 `Now`에서 이번 주 Done Criteria를 만족할 범위만 Weekly Todo로 가져온다. 작업 중에는 한 Step을 시작할 때 `In Progress`, 검증이 끝났을 때만 `Done`으로 바꾼다. 주가 끝나면 결과와 미완료 사유를 남기고 문서를 보존한 뒤, 다음 주에는 새 Todo를 만든다.

Backlog에는 장기 우선순위만 유지하고 세부 실행 로그를 누적하지 않는다. Weekly Todo에는 현재 실행 상태를 유지하되, 긴 결정 근거나 문제 분석은 전용 문서로 옮기고 링크한다.

## 적용 원칙

- 이 문서보다 최신 사용자 결정과 프로젝트별 지침이 우선한다.
- 문서는 사실의 주 저장 위치를 하나만 두고 서로 링크한다.
- 단순한 작업에는 필요한 규칙만 적용하고, 위험과 복잡도가 커질수록 기록과 검증을 강화한다.
- 실제로 실행하지 않은 검증을 완료했다고 표시하지 않는다.
- 절대 경로, 개인 계정, 비밀값, 특정 환경의 식별 정보를 범용 문서에 넣지 않는다.
- 완료 시점에는 결과, 검증, 한계, 다음 Step이 서로 구분되어 있어야 한다.
