# 작은 작업에 검증 기준 적용하기

아래 네 사례는 **설명을 위한 가상 계획이며 실제로 실행한 작업이나 검증 결과가 아니다**. 요구사항·권한·검사 이름도 사례의 가정이다. 대상 프로젝트의 실제 규칙과 명령을 조사한 뒤 바꾸어 사용한다. `Pass` 로그나 수치는 만들어 넣지 않는다.

## 1. 영향이 작은 문서 수정

**요청:** 설치 안내의 오탈자 한 곳을 고친다. 명령·링크·동작 설명은 바뀌지 않는다.

- 인수 조건: 사용자가 지정한 문구가 올바르게 바뀌고 주변 의미가 유지된다. 근거는 수정 요청이다.
- 범위·권한: 해당 문서의 문구 수정과 로컬 확인. 요청에 포함된 가역적 수정이므로 다시 허가를 받을 필요가 없다.
- 필수 검사: 최종 diff에서 지정 문구와 변경 범위를 확인한다. 프로젝트에 문서 필수 검사가 있으면 함께 실행한다.
- 기록: Step에 수정 목적, 최종 파일 상태, 실제 확인 방법과 결과를 짧게 남긴다.

이 작업을 위해 새로운 테스트 도구나 mutation 검사를 추가하지 않는다. 완료는 위 확인을 실제로 수행한 뒤 판단한다.

## 2. 소비자 흐름에서 동작 조건 도출

**요청:** 초대 링크를 사용해 가입하되 만료된 링크는 거부한다.

예시에서는 확정된 초대 정책이 다음과 같다고 가정한다. 실제 작업에서는 정책의 문서나 사용자 결정을 먼저 확인한다.

| ID | 조건과 기대 결과 | 근거 | 필요한 확인 |
|---|---|---|---|
| A1 | 유효한 링크는 만료 시각 직전까지 가입을 허용한다 | 초대 정책 | 시간을 고정한 정상 사례 |
| A2 | 만료 시각과 같거나 이후이면 가입을 거부한다 | 초대 정책 | 경계·직후 사례, 서버 API 직접 호출 |
| A3 | 거부 시 계정·권한 상태가 바뀌지 않는다 | 가입 계약 | 실패 전후 상태 확인 |
| A4 | UI에서 만료 사유를 보고 다음 행동을 알 수 있다 | 사용자 흐름 | 실제 화면의 오류 상태 확인 |

작업 순서는 UI 흐름 → 서버 계약 → 필요한 상태 변경 → 검증이다. 성공 화면만 확인하거나 현재 구현의 비교 연산을 그대로 기대 결과로 복사하지 않는다.

계획에는 프로젝트에서 확인한 실제 검사 명령과 환경을 적는다. 실행 기록에는 검사한 소스 상태를 연결하고, 최종 변경에서도 그 결과가 유효한지 확인한다. 관련 코드·테스트·설정이 바뀐 검사는 다시 실행한다. 단위 검사 통과만으로 서버 연결이나 UI 검증까지 완료했다고 표시하지 않는다.

중요한 경계 검사에 검출력이 더 필요한 경우에만 비교 연산의 변형을 테스트가 잡는지 확인한다. Mutation 점수는 만료 정책 자체가 올바른지 대신 결정해 주지 않는다.

## 3. 버그를 회귀 검사로 남기기

**관찰할 문제:** 만료 시각과 정확히 같은 순간에도 초대가 허용된다는 신고가 있다.

1. 확정된 정책과 재현 가능한 입력·시각을 확인한다. 신고만으로 원인을 단정하지 않는다.
2. 같은 시각에서 가입이 거부되어야 한다는 검사를 준비한다.
3. 수정 전 코드에서 해당 버그 때문에 검사가 실패하는지 실행해 확인한다. 환경 오류나 실행 실패를 버그 재현으로 대신하지 않는다.
4. 허용된 범위에서 원인을 수정하고 동일 검사와 관련 필수 검사를 실행한다.
5. 실제 수정 전·후 코드 상태와 실행 증거를 Todo에 연결한다. 재현할 수 없었다면 그 한계를 그대로 기록한다.
6. Troubleshooting에는 원인·해결·회귀 검사 위치를 남기고 긴 로그는 복제하지 않는다.

이 예시는 아직 실행되지 않았으므로 수정 전 `Fail`이나 수정 후 `Pass`가 관측되었다는 뜻이 아니다. 실제로 두 상태를 관측해야 red/green 증거로 사용할 수 있다.

검사가 실패한다고 기대값을 허용으로 바꾸면 정책 위반을 숨기게 된다. 정책이 정당하게 변경되었다면 변경 근거와 영향을 먼저 기록하고 인수 조건도 함께 갱신한다.

## 4. 구현 가능하지만 고위험 검증이 막힌 경우

**요청:** 저장 구조를 바꾸는 migration을 작성한다. 이 사례에서는 로컬 코드 작성과 격리된 복제 환경의 검증은 허용되었지만 운영 실행 권한은 없다고 가정한다.

- 인수 조건: 변환 후 필수 데이터가 보존되고, 호환성이 유지되며, 실패 시 정해진 복구 방법을 실행할 수 있다.
- 필수 검사: 관련 코드와 데이터 경계 검토, 대표 복제 데이터의 변환 검증, 실패·복구 절차 확인. 실제 항목은 프로젝트 위험에 맞게 정한다.
- 차단 상황의 가정: 복제 데이터에 접근할 수 없어 보존·복구 검사를 실행할 수 없다.
- 가능한 진행: 허용된 로컬 구현·정적 확인·검증 절차 준비는 진행한다. 접근 문제를 해결하려고 운영 데이터나 권한 설정을 임의 변경하지 않는다.
- 상태 기록: 로컬 구현을 마쳤더라도 `Implementation: Complete`, 필수 검증은 `Blocked`, 요청에 없는 운영 배포는 `Out of Scope`로 구분한다. Step은 `Done`이 아니다.
- 다음 Step: 필요한 복제 데이터와 환경 접근을 확보한 뒤 필수 검사를 수행한다. 운영 실행은 별도로 확인된 권한 범위에서 진행한다.

위 상태는 가정한 상황의 기록 방법이며 실제 실행 결과가 아니다. 권한이 이미 확인된 작업마다 재승인을 받는 절차도 아니다. 현재 권한과 위험 경계 안에서는 자율적으로 진행하고, 경계를 넘는 작업만 멈춘다.
